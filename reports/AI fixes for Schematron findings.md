# Rules find, AI proposes, validators decide

Every product studied keeps **detection rule-based and uses AI only to propose the fix**, and the leaders gate that AI with a deterministic check: GitHub Copilot Autofix counts a fix as good only if the alert disappears, no new alert appears and syntax and tests still pass ([GitHub blog](https://github.blog/2024/06/fixing-security-vulnerabilities-with-ai/)). Sonar allows AI fixes only for rules it has certified ([Sonar docs](https://docs.sonarsource.com/sonarqube-server/2025.2/user-guide/rules/rules-for-ai-codefix)), and Semgrep shows a fix only above a confidence threshold that an admin sets ([Semgrep docs](https://semgrep.dev/docs/semgrep-assistant/overview)). In the XML content world, Oxygen is the reference design. It offers rule-authored Schematron Quick Fixes (SQF), an AI Positron "Fix" action on a single validation problem or a multi-selection, and AI functions that can sit inside an SQF replace ([Oxygen blog](https://blog.oxygenxml.com/topics/ai_xpath_functions.html)). The CCMS vendors are thinner: Heretto Etto fixes only "some" DITA validation errors in one topic, Acrolinx rewrites whole sentences, and Tridion, Paligo and MadCap IXIA show no AI fix for validation findings. **No product in scope publishes accuracy or acceptance rates, and none documents re-running Schematron on an AI fix before showing it.** That gap is the opening for AEM Guides Content Health. The recommended design keeps SQF as tier 1. It adds an on-demand AI fix only for an allowlist of rules without an SQF, sends the model the smallest possible context, and accepts a suggestion only if it parses, passes DTD validation, clears the original finding with no new findings, and leaves text outside the flagged span unchanged. A person then applies it through the same "element still matches" anchor check the editor already uses. All of this sits behind an explicit admin opt-in for sending content to a model.

## Oxygen pairs authored quick fixes with AI that targets a specific problem

SQF is a Schematron extension. Its operations are add, delete, replace and stringReplace, plus user-entry, call-fix and parameters, and copy-of replaced keep in the 2018 draft. It is a **W3C Community Group draft, not a standard**, and its main implementations are Oxygen and Escali ([SQF spec](https://schematron-quickfix.github.io/sqf/publishing-snapshots/April2015Draft/spec/SQFSpec.html); [W3C CG](https://www.w3.org/community/quickfix/2018/03/08/release-second-draft-of-schematron-quickfix-specification)). The spec draws two lines Content Health should keep. It does not allow **more than one fix on the same error at once**, and it says conflicts between different fixes "cannot be resolved automatically." SQF is deterministic, but a fix exists only where a rule author wrote one. That is the coverage gap AI fills.

Oxygen fills that gap in three ways. **AI Positron Fix** is triggered by right-clicking a problem in the Results pane. It works from the validation message, including custom Schematron text, so no SQF has to be written ([Oxygen 2025 slides](https://www.oxygenxml.com/events/2025/ai_powered_development_part_1.pdf)). It uses RAG over the current document, and recent releases accept a multi-selection of problems "in a single operation" ([Positron what's new](https://www.oxygenxml.com/ai_positron/whatisnew5.0.html)). **Fix Validation Problems** is an agent action that works on the whole document, with a preview before saving ([what's new](https://mail.oxygenxml.com/ai_positron/whats_new.html)). The agent's save path re-runs validation automatically and feeds the errors back to the model so it can correct itself ([Vibing with AI Positron](https://blog.oxygenxml.com/topics/vibing_with_ai_positron.html)). The third, rule-embedded AI, is the most interesting hybrid. `ai:verify-content` can serve as an assert, and `ai:transform-content` can supply the text inside an `sqf:replace`. The rule author decides *where* and *what* to fix, and the model supplies only the wording, for example shortening a shortdesc or rewriting passive voice. Responses are cached and a request threshold triggers a confirmation dialog ([Oxygen blog](https://blog.oxygenxml.com/topics/ai_xpath_functions.html)). Review goes through Oxygen's XML-aware diff, and since version 8.4 (Sep 2026) AI edits arrive as **tracked changes** when tracking is on. Version 8.4 also added a `validate_with_schematron` agent tool, in early access ([what's new](https://www.oxygenxml.com/ai_positron/whatisnew5.0.html)). Enterprises can bring their own provider or a private LLM and block models ([Positron add-on](https://oxygenxml.com/addons/AI_Positron.html)). Two things are not documented: whether the single-problem Fix re-validates before it shows a result, and exactly what context goes to the model.

## CCMS vendors offer suggestions but no validation loop

Paligo runs a DocBook schema, its bundled recommended Schematron rules and any uploaded custom Schematron, and blocks saving until the topic passes all of them, but it documents no fixes ([Paligo docs](https://docs.paligo.net/en/validation.html)). Heretto's **Etto** responds to a natural-language prompt on selected content and fixes "some" DITA validation errors. It works on **one topic at a time** and cannot fix errors that depend on other files or create files or links. Its output arrives as suggested changes with Accept, Reject and Revise, and repeating a prompt can give different results. Each request is capped at 16k input and 4,096 output tokens, with monthly quotas of 600k input and 150k output tokens, and Heretto tells users to have a person review all AI output ([Heretto Etto](https://help.heretto.com/heretto-ccms/create/etto-the-heretto-copilot)). Acrolinx (now Markup AI), which already integrates with AEM Guides, offers "Get Suggestion" per issue card. When several issues share a sentence or paragraph, it **rewrites the whole sentence or paragraph** ([Markup AI support](https://support.markup.ai/hc/en-us/articles/18247945921298)). Its release notes show failures that come from anchors going stale: suggestions that failed to apply while the card vanished, and replacements that overwrote manual edits ([release notes](https://support.markup.ai/hc/en-us/articles/24053730060690-Sidebar-Release-Notes); [Sheets overwrite](https://support.markup.ai/hc/en-us/articles/10221284651794-Why-do-replacements-from-the-Sidebar-overwrite-my-manual-edits-in-Google-Sheets)). Tridion Docs offers AI for tagging and drafting only ([RWS](https://rws.com/content-management/tridion/tridion-and-ai)). MadCap IXIA CCMS ships AI Positron mainly for finding duplicate content ([MadCap blog](https://madcapsoftware.com/blog/madcap-ixaccms-ai-positron)). AEM Guides' own smart suggestions use default thresholds of 0.6 (tag level) and 0.7 (file level), and the docs state that "external AI tools are not used" ([Experience League](https://experienceleague.adobe.com/en/docs/experience-manager-guides/using/user-guide/ai-assistant-aem/authoring-ai-based-smart-suggestions)). That data-handling stance is a precedent Content Health must not quietly break.

## Code autofix tools show how to make an AI fix verifiable

The code-security tools publish the most concrete engineering. Copilot Autofix sends a **narrow context**: the rule help, the alert message and location, the code snippets along the data flow, and each file's imports. The model may edit only code that is in the prompt. It returns **before/after blocks rather than diffs**, because the model got line numbers wrong. A post-processor fuzzy-matches the anchors and runs parser and type checks. Narrowing the context **tripled the success rate while cutting compute 6x**, and suggestions are cached ([GitHub blog](https://github.blog/2024/06/fixing-security-vulnerabilities-with-ai/)). Median time to fix fell from 1.5 hours to 28 minutes ([TechTarget](https://www.techtarget.com/cybersecurity/news/366603045/GitHub-Copilot-Autofix-tackles-vulnerabilities-with-AI)). GitHub never published an absolute acceptance rate. The current docs split a free fix for a single alert from an agentic fix that re-runs CodeQL and costs credits. They also say validation **cannot confirm fixes for custom queries**, which is exactly the situation of a customer's own Schematron ([GitHub Docs](https://docs.github.com/en/code-security/concepts/code-scanning/copilot-autofix-for-code-scanning)). Snyk rescans each candidate fix for the original issue and for new ones; its "about 80%" accuracy figure is marketing ([arXiv 2402.13291](https://www.arxiv.org/pdf/2402.13291)). Ruff's deterministic split between **safe and unsafe fixes** is a model for labeling: only safe fixes apply by default ([Ruff blog](https://astral.sh/blog/ruff-v0.1.0)).

Text rules carry a different risk. Research on LLM grammar correction finds that models **overcorrect**, rewriting spans that were already correct and shifting meaning. Benchmarks for minimal edits weight precision above recall for that reason, and mitigations include majority voting at the level of individual edits ([arXiv 2506.13148](https://arxiv.org/pdf/2506.13148)). For structure, constrained decoding and validation with retries are the established guardrails ([arXiv 2501.10868](https://arxiv.org/abs/2501.10868v2)). **No benchmark measures LLM repair of DITA against Schematron.** Any accuracy claim for Content Health has to come from its own measurements.

## Recommended design for Content Health AI fixes

The table maps each design question to what the field shows and to a recommendation that fits Content Health's server-computed SQF, the rule that the agent proposes and a person applies, and the requirement for an explicit decision before customer content goes to a model.

| Question | Industry evidence | Content Health choice |
|---|---|---|
| Trigger | Right-click per problem (Positron), per alert (Copilot), on prompt (Etto) | "Suggest AI fix" per finding, plus multi-select within one rule; never generated automatically during a scan |
| Rule-defined vs AI | SQF first; Sonar certifies rules for AI | SQF always wins; AI only for allowlisted rule IDs with no SQF, labeled "AI" |
| Context | Narrow context gave a 6x compute cut (Copilot) | Assert/report text, rule description, flagged element XML, parent path, DTD content model; never the whole topic or map |
| Output | Before/after blocks, not diffs | Replacement for the flagged element only, expressed as an SQF-style operation |
| Validation | Alert gone, no new alerts, parse ok (Copilot); rescan (Snyk) | Parse, then DTD, then re-run the same Schematron: the finding is cleared and no new findings appear; text outside the span is identical; 1 retry with the error fed back; otherwise "no fix" |
| Confidence | Computed confidence with an admin threshold (Semgrep) | Computed from the validation result and edit size, not the model's self-rating |
| Review/apply | Diff and tracked changes (Oxygen 8.4); Accept/Reject (Etto) | XML-aware diff in the editor; person applies; existing check that the element still matches rejects stale anchors |
| Batching | Positron multi-select; SQF bans several fixes on one error | Batch only findings from the same rule, one fix per finding, re-validate after each apply |
| Cost | Caching (Copilot, Oxygen); token quotas (Etto) | Cache by hash of (rule ID, element XML); per-tenant quota; skip the AI when an SQF exists |
| Data | Bring your own LLM (Positron); no external AI (Guides smart suggestions) | Off by default; admin opt-in per tenant naming the model endpoint; nothing used for training |

Structure (code-like) rules suit this design best because the validator is deterministic. A fix either clears the assert and passes the DTD or it is discarded. Text rules such as passive voice, shortdesc length or terminology need a further constraint. The fix must be a **minimal edit within the flagged text node**. Any edit that touches markup or text outside the node is rejected, and every changed word is highlighted in the diff. When a text rule is decided by `ai:verify`-style logic rather than by XPath, re-validation is itself nondeterministic. Such fixes should be labeled "unsafe" in Ruff's sense and never applied in bulk. The Oxygen pattern of `ai:transform-content` inside `sqf:replace` is worth adopting for these rules. The rule author keeps control of scope while the model writes only the wording, and the existing SQF apply path is reused. Telemetry should copy GitHub's set: the share of findings with a suggestion, the validation pass rate, and how many suggestions are accepted as-is, edited or dismissed. Rules should be promoted onto the allowlist only on measured evidence.

## Conclusion

The industry's weak point is not generating fixes but **proving them**. Content Health holds an advantage that CCMS rivals do not use: it already owns the exact rule, the server-side validator and an apply step that checks anchors. Re-running the originating Schematron on every AI candidate before a person sees it would make Content Health, as far as public documentation shows, the first content platform to offer *verified* AI fixes for Schematron findings. That is a stronger story than "AI fixes" alone, and it is directly measurable.

What remains unknown matters for planning. No vendor publishes fix accuracy, no DITA repair benchmark exists, and per-fix cost data is absent. The first milestone should therefore be an offline harness in Copilot's style, run over real findings for a handful of structure rules. It would produce the pass rate needed to justify the allowlist and the data-handling opt-in.
